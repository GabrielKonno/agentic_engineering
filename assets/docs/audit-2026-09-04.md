**Two structural remedies the evidence names directly, in order of leverage.**

**(1) Extend the back-sweep from rules to CONTROLS.** The checklist already mandates that a newly
promoted *rule* be swept against every artifact it retroactively governs. Nothing does this for a
newly promoted *control*. When a batch installs or amends a check, gate or report key, every other
control in the checklist must be re-run against that batch's own artifacts before commit. Every
finding above would have been caught by it; nothing else caught any of them.

**(2) A check must be proved by NEGATION before it is trusted, and the proof must be a command.**
`component-design §9` rule 4 already says this. Three checks shipped this batch that **cannot
fail**: the D7.5 wrong-directory guard (`Q-2`), the key-list staleness grep (`Q-10`), and Gate 4's
harvest regex for a whole class of key names (`Q-39`). All three were written with a stated
expected result and none was run against a state that should make it red. A green from a check that
cannot go red is not evidence, and three of this run's controls have been emitting exactly that.

**A third observation, offered without a remedy because the evidence does not name one.** The single
finding of this run that no control could have caught is `Q-17`: a fix that WAS applied, then undone
by a `git checkout --` revert aimed at an unrelated over-correction in the same file, with the redo
covering only the other finding's sites. Nothing in this repo reconciles what a partial revert
undoes against what is re-applied. It is a real gap, it is narrow, and inventing a control for it
in the same batch that discovered it would be the exact mistake this report has spent forty findings
documenting.

not move, the seam model is wrong too, and the next hypothesis should be that the defect rate is a
